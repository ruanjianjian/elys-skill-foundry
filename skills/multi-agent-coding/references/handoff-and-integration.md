# 波次复核、白话披露与集成收口

## 波次与任务交接

任务单使用 work-orders-and-iteration 的唯一模板。五段派发正文：一句话目标 → 已确认 repo/worktree/base 与权限 → 唯一契约/方案/验收文件路径 → 关键语义与可复用先例 → 停止条件/完成通知/交付方式。

简报完全自包含；没有跨机文件访问时，在用户授权范围传递必要脱敏内容，不能只给 worker 无法访问的本机路径。不得为方便同步上传凭证。

Lead 收到结果先核对：所有变更路径、是否越界、契约/fixture 版本、准确 head、运行证据、自审意见、剩余阻塞。真实必需证据缺失的任务不得打开依赖该证据的下游门控；不相关独立任务可继续。

每个复核过关的任务写一份短的 `explainers/<id>.md`：

- 做了什么、之前与之后。
- 数据从哪里来 → 怎么处理 → 存哪里 → 谁消费。
- 关键选择及其用户可感知影响。
- 四列验证表或唯一 validation-log 中相应用例链接。
- 未验证部分与剩余风险。

披露不阻塞无关下游，但交付前不能欠账。不要复制测试结论形成第二个真源。

## 接缝与外部冲突

按产出者 → wire/DTO/mapper → 消费者 → 用户结果审查：空凭据/租约、未消费字段、空集合校验假通过、身份/错误分支丢失、旧版本兼容。审查者独立于对应实现者更有价值；分派只读审查仍遵循已确认执行方式。

涉及横切机制时，列机制 × 写入路径矩阵；集成时补充期间 base 新增的相关路径。对重叠外部在途分支，在隔离 worktree 做合并预演并跑相关回归，未经授权不改对方分支。发现冲突的修复归属由 Lead 明确，不能把他人项目工作默默揽进来。

收口前 fetch 并检查基线变化；吸收必要变化后重新验证，保护 dirty worktree，不以强推解决人类共写冲突。评审意见先核实可复现事实再修复，不机械追随 bot，也不同时把同一片代码派给两名修复者。

## PR 规划与候选

默认一仓一个集成交付单元。只有独立可用、可测、可回滚且不共改公共文件的切片才适合拆 PR；存在新代码依赖链的任务应整体集成。跨平台产物能否拆分也要满足这个条件，不单凭 iOS/Android 名称。

worker 只交其获授权的分支/补丁；Lead 可在授权范围 commit/push 集成候选，PR 由交付流程接管。所有进入候选的代码、测试、证据索引和文档在人类验收前定稿。验收记录保存在候选外，避免“为记 accepted SHA 又改 HEAD”。若已有 ELYS checkpoint 工具，读取当前说明后使用。

交付给 engineering-delivery：repo、base、集成 branch、任务台账目录、validation-log 的真实路径（旧项目可为 test-matrix）、accepted_head_sha、acceptance record、未解决风险。遵循该技能当前接口，不为了字段命名再复制一份测试矩阵。

Delivery 因追 base、冲突或审修改变 HEAD 时，检查实际影响、重新验证受影响路径并执行 STOP Review（适用时）。人工验收延续按 `engineering-delivery/references/acceptance-continuity.md`；旧通过保留为历史证据，不伪称为新 head 实测，也不单因 SHA 变化重复索要确认。

## 结束与后续

overview 汇总目标、模块、决策、披露、准确版本与剩余事项；最终 PR URL 写候选外记录，或经授权另走文档变更，不能使已验收候选悄悄变动。目标若包括 review/合并，持续治理到真实状态满足，不以创建 PR 当完成。

合并后不向已结束分支 push；新工作基于默认分支。仅清理本任务且明确允许清理的资源；不要结束其他 worker 或删除共用 broker。经验留在项目决策/验证记录，未经明确请求不更新用户长期记忆或对外发布。
